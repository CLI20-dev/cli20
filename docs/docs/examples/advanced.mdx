# Advanced

This is the reference example for explicit action-pipeline composition. Use it
when the sugar aliases are close but not quite enough.

It is the page to open when you need to understand the lower-level building
blocks behind cli20's higher-level aliases.

## What This Example Shows

This example builds parsing behavior from explicit conversion, validation, and
storage steps instead of the higher-level aliases. It is the pattern to copy
when you need lists, uniqueness, filesystem checks, or a runtime default for
an option value with precise control over how values are stored. On success, it
produces optional `config`, `jobs` with a default of `1` (or a
`nproc_dummy()` value when `-j` is provided without a value), plus collected
`includes` and `defines`.

## Try It

The virtual filesystem is configured like this in this environment:

```
/
├── config.toml   (regular file)
└── configs/      (directory)
```

<ExamplePlayground
  name="advanced"
  defaultArgs="--config config.toml -I /include -D DEBUG"
  setupFs={setupAdvancedFs}
/>

Things to try:

- **Happy path** — `--config config.toml -I /include -D DEBUG`
- **Default jobs** — `--config config.toml` to see the `1` default
- **Explicit jobs** — `--config config.toml --jobs 8` to override the runtime default
- **Multiple defines** — `--config config.toml -D FOO -D BAR -D FOO` to see `push_unique` deduplicate
- **Directory as config** — `--config /configs` to see `is_regular_file` reject it
- **Out-of-range jobs** — `--config config.toml --jobs 99` to see range validation fail
- **Missing jobs value** — `--config config.toml --jobs` to see the example fall back to `nproc_dummy()`
- **Missing parent** — `-I /usr/include` to see `parent_exists` fail (`/usr` doesn't exist in the virtual FS)
- **Help** — `-h` or `--help`
