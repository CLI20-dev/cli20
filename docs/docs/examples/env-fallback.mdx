# Env Fallback

Options can be populated from environment variables when they are not provided
on the command line. The `.env` field on any option names the environment
variable to check. The same type conversion and validation pipeline runs
regardless of whether the value came from the CLI or the environment.

## What This Example Shows

- **`--threads` / `NUM_THREADS`** — an integer option with `range<1, 32>`
  validation. If `NUM_THREADS` is set in the environment, it is parsed and
  validated exactly like a CLI argument. A value outside 1–32 is an error.
- **`--config` / `CONFIG_FILE`** — a string option with `matches<".*\\.toml">`
  validation. The env value must end in `.toml` or parsing fails.
- **`--verbose` / `VERBOSE`** — a flag. When the env var is present (any
  value), the flag is set to `true`.
- **CLI takes precedence** — if the option is supplied on the command line,
  the environment variable is ignored.

## Try It

Edit the environment variables in the panel below, then run the program.

The virtual filesystem for this playground contains the following config files
you can reference as `CONFIG_FILE`:

| Path | Notes |
|---|---|
| `dev.toml` | local development |
| `test.toml` | test environment |
| `staging.toml` | staging environment |
| `prod.toml` | production |

<ExamplePlayground
  name="env_fallback"
  defaultArgs="build-job"
  setupFs={setupEnvFallbackFs}
  initialEnv={{NUM_THREADS: '4', CONFIG_FILE: 'dev.toml'}}
/>

Things to try:

- **Switch environment** — change `CONFIG_FILE` to `staging.toml` or `prod.toml`
- **CLI overrides env** — `--config test.toml build-job` while `CONFIG_FILE` is set
- **Validation via env** — set `NUM_THREADS=99` to see a range error
- **Bad config name** — set `CONFIG_FILE=settings.json` to see the regex fail
- **Verbose from env** — add `VERBOSE=1` and run `build-job`
- **Help** — `--help`
